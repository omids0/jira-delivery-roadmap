# طراحی — نقشه راه تحویل Jira

این سند هدف، معماری و نقشه‌ی راه ساخت را ثبت می‌کند. وضعیت فعلی کد: **اسکلت** (بوکمارک، اتصال به Jira، انتخاب پروژه). موتور برنامه‌ریزی هنوز نوشته نشده.

## هدف

یک نقشه‌ی راه تحویل برای **هر پروژه‌ی Jira Data Center**: کوتاه‌ترین مسیر برای بستن همه‌ی استوری‌های باز، با توجه به وابستگی‌ها و ظرفیت تیم بک‌اند و فرانت. با بوکمارک در صفحه‌ی Jira اجرا می‌شود، با سشن لاگین خود کاربر (بدون توکن، بدون سرور، بدون CORS) و پروژه از یک سلکت‌باکس انتخاب می‌شود. همان الگوی ریپوی `jira-status-dashboard`.

## نمونه‌ی مرجع

یک نمونه‌ی کار برای یک پروژه‌ی خاص ساخته شده بود (یک صفحه‌ی HTML تکی که دیتای پایه‌ی همان پروژه داخل کدش ثابت بود و فقط وضعیت باز/بسته را از Jira تازه می‌کرد). فایلش به‌صورت محلی در `reference/` است و **عمداً داخل git نیست**، چون دیتای شرکتی دارد (اسم اپیک‌ها، عنوان استوری‌ها، اسم نفرات). این پروژه همان ایده را **عمومی و زنده** می‌کند: هیچ دیتای پروژه داخل کد نمی‌ماند.

## قابلیت‌های هدف (از روی نمونه‌ی مرجع)

| بخش | چه نشان می‌دهد |
|---|---|
| KPI و what-if | تاریخ تحویل، تعداد روز کاری باقی‌مانده، اثر تغییر تعداد نفرات یا سناریوی سرعت |
| نقشه‌ی کلی | هر اپیک از اولین استوری بسته‌شده تا تاریخ تحویل برنامه‌ریزی‌شده؛ نمودار هفتگی استوری‌های بسته |
| سرعت واقعی تیم | تعداد ساب‌تسک Done به ازای هر روز کاری، از اسپرینت‌های بسته‌شده |
| فلوچارت وابستگی | ردیف = اپیک، ستون = گام؛ کلیک روی کارت پیش‌نیازها و وابسته‌ها را نشان می‌دهد |
| خط زمانی نفرات | swimlane هر نفر؛ مسیر بحرانی با کادر پررنگ |
| تخصیص اپیک به نفرات | یک مسئول BE و یک مسئول FE برای هر اپیک؛ بقیه خودکار به کم‌کارترین نفر |
| کارهای باز هر نفر | همه‌ی آیتم‌های assign‌شده و Done‌نشده، مستقل از اسپرینت |
| جدول تحویل هر اپیک | تاریخ‌ها بر اساس ترکیب تیم انتخاب‌شده |
| اسپرینت پیشنهادی بعدی | ۱۰ روز کاری؛ اول مسیر بحرانی، بعد اپیکی که کمتر کار در جریان دارد |
| ماتریس اسپرینت‌ها | هر اپیک در هر اسپرینت چند استوری تحویل می‌دهد |

## قواعد محاسبه (از نمونه‌ی مرجع)

- **واحد برآورد:** تعداد ساب‌تسک، تبدیل‌شده به روز با سرعت تیم (ساب‌تسک Done به ازای نفر در روز کاری).
- **سناریوی سرعت:** میانگین اسپرینت‌های قبل، خوش‌بینانه، محتاطانه.
- **نقش هر ساب‌تسک:** از component (BE / FE)؛ اگر نبود، حدس از عنوان.
- **فرانت قرارداد-اول:** وقتی نیمی از کار بک‌اند همان استوری تمام شد، فرانت شروع می‌کند و دست‌کم یک‌دهم روز بعد از پایان بک‌اند تحویل می‌دهد.
- **موازی‌کاری:** هر نفر چند خط موازی دارد ولی خروجی روزانه‌اش بین خط‌ها تقسیم می‌شود (موازی‌کاری کل کار را کم نمی‌کند). دو استوری از یک اپیک هم‌زمان روی یک نفر نمی‌نشیند.
- **تقویم کاری:** قابل تنظیم (پیش‌فرض: شنبه تا چهارشنبه).
- **لیبل‌های معنادار:** needs-decision، deferred، phase-2/3، cancelled، و لیبل‌های تعیین‌کننده‌ی BE/FE. اسم‌ها باید در کانفیگ هر پروژه قابل تغییر باشند.
- **وابستگی بیرونی:** استوری‌ای که منتظر تیم دیگر است، جدا علامت می‌خورد.

## معماری

```
src/
  jiraClient.js        GET با کوکی سشن (fetch same-origin) + صفحه‌بندی JQL
  projectConfig.js     defaults + override هر پروژه از config/projects.json
  browser/
    main.js            ورودی بوکمارک
    overlay.js         overlay تمام‌صفحه با iframe
    app.js             انتخاب پروژه، فراخوانی Jira، رندر
  render/
    shell.js           قالب صفحه‌ها (رشته‌ساز خالص، بدون DOM)
config/projects.json   تنظیمات پیش‌فرض و override هر پروژه
site-src/index.html    صفحه‌ی نصب بوکمارک
scripts/build-site.js  esbuild → site/roadmap.js + index.html
```

## وضعیت پیاده‌سازی (v0.3)

همه‌ی قابلیت‌های جدول بالا پیاده‌سازی شده‌اند:

```
Jira REST ──collect.js──► raw ──model.js──► model ──adapter.js──► ctx ──engine.js──► plan P ──render/*──► HTML
                                  (stories, ساب‌تسک‌ها، لینک‌ها)        (اپیک‌ها، سرعت، نفرات)   (زمان‌بند، مسیر بحرانی)   (بخش‌های صفحه)
```

- `sprints.js`: سرعت واقعی از اسپرینت‌های بسته‌شده‌ی Scrum board (Agile REST)؛ بدون سابقه، سرعت فرضی از کانفیگ.
- `engine.js`: همان زمان‌بند نمونه‌ی مرجع (اولویت مسیر بحرانی، مسئول هر اپیک، چند خط موازی، فرانت قرارداد-اول).
- `browser/roadmap-ui.js`: صفحه یک بار رسم می‌شود و کنترل‌ها بخش‌ها را در جا بازسازی می‌کنند. وضعیت (تعداد نفرات، سناریو، تخصیص اپیک) در `localStorage` هر پروژه ذخیره می‌شود.
- `npm run build:site` سایت را می‌سازد؛ `node scripts/preview.js` پیش‌نمایش روی دیتای ساختگی می‌سازد (بدون Jira).

## قدم‌های بعدی (پیشنهادی، قدیمی)

1. ✅ **مدل داده (انجام شد: `src/collect.js`، `src/model.js`):** `collect` که برای یک پروژه اپیک‌ها، استوری‌ها، ساب‌تسک‌ها، لینک‌ها و assignee را از Jira بخواند و به یک مدل داخلی نرمال کند (تابع خالص، قابل تست با JSON).
2. **سرعت تیم:** از `/rest/agile/1.0/board/{id}/sprint` و ساب‌تسک‌های Done تا تاریخ بستن اسپرینت.
3. **زمان‌بند:** گراف وابستگی، گام‌بندی (topological levels)، زمان‌بندی نفرات، مسیر بحرانی. بدون DOM، با تست واحد.
4. **رندر:** KPI → خط زمانی نفرات → فلوچارت → اسپرینت پیشنهادی.
5. **تنظیمات تیم:** تعداد BE/FE، نام نفرات و تخصیص اپیک، ذخیره در `localStorage`.

## ریسک‌ها / سؤال‌های باز

- **وابستگی‌ها:** در نمونه‌ی مرجع دستی ثبت شده بودند. روی پروژه‌ی عمومی باید از `issuelinks` (مثلاً «is blocked by») بیایند؛ اگر پروژه لینک‌ها را تمیز پر نکرده، نقشه ناقص درمی‌آید. باید حالت «بدون وابستگی» هم کار کند و صریح بگوید.
- **برآورد:** ساب‌تسک‌های هنوز ساخته‌نشده دیده نمی‌شوند. باید برآورد پیش‌فرض برای استوری بدون ساب‌تسک داشته باشیم.
- **اسپرینت‌ها:** پروژه‌ای که Scrum board ندارد سرعت واقعی ندارد؛ باید سرعت پیش‌فرض را از کانفیگ بگیرد.
- **مقایسه با نمونه‌ی مرجع:** اولین پروژه‌ی تست همان پروژه‌ای است که نمونه برایش ساخته شده؛ خروجی باید با نمونه جور دربیاید.
- **CSP:** اگر Jira اسکریپت خارجی را مسدود کند، بوکمارک کار نمی‌کند (همان محدودیت پروژه‌ی خواهر).
